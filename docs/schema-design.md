# Prisma schema design — SourcingPick v1

**Status:** superseded by the code. This was the original design note; the schema at [prisma/schema.prisma](../prisma/schema.prisma) has since moved well past it and is the source of truth. 71 migrations are applied. Read this for intent, not for current shape.

## What this models

All 17 entities from spec §3.1, plus three the spec implies but doesn't list in §3.1:

- **TenderInvitation** (spec §4.3 — the appel d'offres invite sent from agent to factory)
- **AgentTask** (spec §9.3 dashboards — the agent to-do list)
- **EmailOtp** (our own — needed for email-OTP 2FA, not in spec)

Plus the Auth.js v5 / Prisma adapter tables: `Account`, `Session`, `VerificationToken`. Our `User` model is extended to satisfy Auth.js's required field shape while carrying our domain fields.

**Total models:** 22. **Total enums:** 18.

## Key design decisions

### 1. IDs — cuid2 internally, human-readable references for public-facing IDs

Two parallel ID systems:

- **Internal:** every row has `id String @id @default(cuid(2))`. cuid2 over UUID because they're shorter, URL-safe, sortable-ish, and index well in Postgres. The spec says "uuid" but doesn't actually depend on it being a UUID — what matters is uniqueness and indexability.
- **Public:** entities the user sees mentioned (requests, orders, invoices, escrow, payouts, certifications, marketplace items) carry a separate `reference` string field with the spec's format (`REQ-XXXXXX`, `ORD-XXXXX`, `INV-YYYY-NNNN`, `ESC-YYYY-NNNN`, `PAY-YYYY-NNNN`, `CERT-YYYY-NNN`, `MKT-XXX`). Generated by app code at create-time, uniqueness enforced by `@unique`. Internal IDs never leak into emails, PDFs, or URLs.

### 2. Money is integer cents, never decimals

Every monetary amount is `Int` and named `*Cents` (e.g., `unitPriceCentsClient`, `totalCents`, `commissionCents`). Reasons:

- No decimal-math surprises. `0.1 + 0.2 != 0.3` is a category of bug we don't want.
- Matches Stripe's API patterns 1:1 — when we wire the payment provider in Phase 3, no conversions needed.
- Trivial JS serialization (no Prisma `Decimal` import on every client component).
- Format-at-the-edges via `formatEUR()` from `src/lib/i18n/formatters.ts`.

Currency is **always EUR in v1** — stored implicitly. If we ever add multi-currency, we add a `currency String @default("EUR")` column.

### 3. Sub-roles are a single union enum, not 4 separate ones

Spec mixes them: a User has a `Role` (CLIENT / FACTORY / AGENT / ADMIN) AND a `SubRole` (OWNER / MEMBER / ACCOUNTANT / SENIOR / SUPER). Different sub-roles are valid for different roles (e.g., ACCOUNTANT only makes sense for CLIENT and ADMIN). One union enum keeps the schema simple; the role/sub-role validity matrix is enforced in `src/lib/permissions/`. Trying to split into four enums would either need polymorphic relations (Prisma doesn't do those cleanly) or duplicate fields.

### 4. Soft delete only where it matters

Most rows are hard-deleted. We keep `deletedAt DateTime?` only on:

- `Organization` and `User` — preserves history for audit and avoids broken foreign keys on completed transactions
- `Message` — spec explicitly says messages support soft-delete (spec §7.2)
- `MarketplaceProduct` — products go to `ARCHIVED` rather than disappearing
- `Notification` — kept until purged by a cron, not actually soft-deleted (just `read`)

The rest hard-delete via `onDelete: Restrict` on relations — accidental deletes get rejected, not silently corrupt state.

### 5. Audit log is append-only

`AuditLog` has no `updatedAt`, no `deletedAt`. App code never updates rows. Postgres-side we can later add a trigger to deny UPDATE/DELETE for extra safety.

### 6. Multi-tenancy is app-level, not DB-level

We don't use Postgres RLS in v1 — every query is filtered by `organizationId` in the data layer. Reasons:

- App-level keeps Prisma queries straightforward and debuggable.
- The spec's permission model is more nuanced than RLS handles cleanly (agents see "their" requests, super-admins see all, accountants see only finance).
- We can add RLS later as belt-and-suspenders without breaking anything.

The `@@index([organizationId, ...])` patterns make org-scoped queries fast regardless.

### 7. State machines live in app code, schema enforces shape

The `status` column on `SourcingRequest`, `Order`, `EscrowTransaction`, etc. uses native Postgres enums. **Valid transitions** between states (spec §3.2) are enforced in `src/lib/<aggregate>/transitions.ts`, not in the DB. Reason: state machines change as the product evolves; redeploying app code is faster than migrating enum check constraints.

### 8. Quote.unitPriceCentsFactory is private to the platform

The spec calls it out: factory price (what the factory quoted), client price (what we show), margin (delta) — only Admin sees `unitPriceCentsFactory` and `marginCents`. The schema stores all three. Hiding them is the data-layer / API layer's job, not the schema's.

### 9. Webhook events — separate model

Adding a `WebhookEvent` model (not in spec). Stores every incoming webhook (Stripe, carriers, etc.) with payload, signature, processed status, retry count. The Admin needs this surface visible per the substance rule — and we need it for replay/debugging anyway. Cheap insurance.

### 10. AuthJS adapter compatibility

The `User` model satisfies both:
- Our domain shape (role, subRole, organizationId, twoFactorEnabled, locale, etc.)
- The Auth.js v5 Prisma adapter required shape (id, name, email, emailVerified, image)

Auth.js extra fields (`name`, `emailVerified`, `image`) are nullable; we map `name` from `firstName + lastName` when needed.

## Indexes

Every foreign key gets an index automatically (Prisma adds them on `@relation` fields). Additional `@@index` declarations target known hot-path queries:

- `SourcingRequest`: `(status, agentId)`, `(clientOrgId, status)`, `(status, createdAt)`
- `Order`: `(status, factoryOrgId)`, `(status, clientOrgId)`
- `Quote`: `(requestId, status)`, `(factoryOrgId, status)`
- `Invoice`: `(organizationId, status)`, `(status, dueAt)` for overdue queries
- `Notification`: `(recipientUserId, read, createdAt)`
- `Message`: `(threadId, createdAt)`
- `AuditLog`: `(actorUserId, createdAt)`, `(targetType, targetId)`, `(level, createdAt)`
- `TenderInvitation`: `(requestId, status)`, `(factoryOrgId, status)`

## What this schema does NOT do yet

- **Full-text search indexes.** Postgres `tsvector` columns + GIN indexes for Message/MarketplaceProduct will be added when we wire search in Phase 2/4. Holding off because the column type and weighting depend on actual UX.
- **Materialized views for dashboards.** Spec §9 dashboards compute aggregations. For v1 we'll do these as straight queries with indexes; materialised views are a Phase 6 optimisation.
- **LISTEN/NOTIFY triggers.** SSE realtime will use Postgres LISTEN/NOTIFY (Phase 2). We'll add the triggers then.
- **CHECK constraints for cross-field rules** (e.g., `Order.balanceCents = totalCents - depositCents`). Enforced in app code for v1; migrate to DB constraints if we hit data integrity bugs.

## Sign-off questions

1. **cuid2 IDs over UUID** — fine, or do you want UUID for some external-integration reason?
2. **Integer cents over Prisma Decimal** for money — fine?
3. **Soft-delete scope** (Organization, User, Message, MarketplaceProduct only) — covers your needs, or extend to others?
4. **WebhookEvent model** added beyond the spec — keep?
5. **Single union SubRole enum** instead of four per-role enums — fine?
